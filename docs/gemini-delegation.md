# 제미나이·GPT 위임 평가

제미나이에 어디까지 맡길지 정한 근거 기록이다. GPT에 맡긴 작업도 같은 표에 모델을 적어 기록한다. 결정 내용은 [CLAUDE.md의 GPT·제미나이 작업 위임](../CLAUDE.md)에 반영했고, 두 문서가 다르면 CLAUDE.md를 따른다. 아래 시험 중 그 규칙의 금지 범위(푸시·수집 저장소)에 든 것은 사용자가 시험용으로 따로 허용한 예외다.

## 결정 (시험 1~5 근거)

- **특징:** 지시한 범위·규칙을 정확히 지킨다. 결과만 정해 줘도 기존 코드를 읽고 맞는 함수를 골라 구현한다. 주어진 기준과 어긋난 곳은 잘 찾는다. 반면 기준 없이 위험·설계 빈틈을 추론하지 못하고, 테스트에서 가장 까다로운 경우를 빠뜨리는 경향이 있다.
- **맡긴다:** 문서·문구·주석 정리(기준이 되는 사실을 주고 어긋난 곳은 보고하게 한다), 정해진 파일의 기계적 수정, 공개 앱 화면·기능의 여러 파일 구현.
- **맡기지 않는다:** 원인 분석·설계 판단, 위험을 스스로 판단해야 하는 일, CLAUDE.md가 제외한 파일·영역(수집기 고정 실행 파일, 토큰·저장소 분리, 외부 JSON 검증·동기화, 푸시, 저장 키·백업 호환, 매매·알림·자산 계산, 워크플로·수집 저장소·`records`).
- **조건:** 프롬프트에는 사용자 입장의 결과, 바꿀 수 있는 파일, 핵심 경우의 테스트를 넣고, "핵심 판단을 일부러 고장 내 테스트가 실패하는지 확인하고 보고한다"를 요구한다. 병합 전에는 Claude나 GPT가 범위·규칙을 확인하고 직접 고장 내 본다. 화면 변경은 AGENTS.md의 캡처 규칙대로 확인한다.

- **증상만 준 수정은 실패:** 8-1은 시험 계획 7(증상만 주는 버그 수정)에 해당한다. 그럴듯한 원인 하나를 정해 확인 없이 고쳤고, 고치면서 문서에 적힌 규칙(요청 횟수)을 깨고 새 버그를 만들었다. 8번에서 스스로 하던 일부러 고장 내 보기도 빠졌다. "원인 분석은 맡기지 않는다"는 지금 규칙과 맞는 결과다.
- **같은 작업을 GPT에 다시 맡김(8-2):** 검토자가 원인과 고칠 방향을 정한 뒤 GPT 6.1 Sol에 맡겼다. 제미나이의 약점(가장 까다로운 경우를 빠뜨린 테스트, 지시 밖 경계 추론)이 이 작업에서는 나타나지 않았다. 다만 설계를 받은 구현이므로 GPT의 원인 분석 능력은 이 사례로 판단하지 않는다. GPT 기록은 이 1건뿐이어서 CLAUDE.md의 GPT 설명은 바꾸지 않았다.
- **GPT가 원인 분석부터 맡은 첫 사례(8-3):** 확인하지 못한 원인은 가설로 남기고 코드로 확인되는 빈틈만 고친 점이 제미나이 8-1과 달랐다. 반면 바꾼 대기·종료 조건이 다른 종료 경로(로그인 필요)에 미치는 영향과, PR 설명과 실제 우선순위의 어긋남은 놓쳤다. 상태·시점을 바꾸는 수정은 프롬프트에 "바뀐 대기·종료 조건이 기존 종료 경로(로그인 필요, HTTP 오류, 시간초과, 정상 응답)마다 어떻게 달라지는지 표로 적고, 경로마다 테스트를 둔다"를 넣으면 막을 수 있다. 이 요령을 넣은 보완 프롬프트에서는 종료 경로마다 테스트를 두고 회귀 없이 고쳤다. GPT 기록이 2건이고 규칙과 어긋난 결과는 아니어서 CLAUDE.md는 바꾸지 않는다.
- **모델 기록:** 8-1까지의 제미나이 버전·수준은 기록하지 않았다. 이후 사례는 모델 칸에 버전·수준을 적는다.
- **상태를 지웠다가 되돌아오는 경로(12번):** 바꾼 조건이 다른 경로에 미치는 영향을 놓친 점은 8-3·10과 같은 유형이다. 이번에는 구현 모델과 다른 GPT 모델이 점검했는데도 남았다. 두 모델 모두 '지워진다'까지만 확인하고 '돌아올 때 무엇이 나가는가'는 보지 않았다. 아래 요령에 왕복 확인을 더했다. CLAUDE.md 규칙과 어긋난 결과는 아니어서 규칙은 바꾸지 않는다.

## 평가 기준

시험마다 아래 항목을 같은 방식으로 기록한다.

1. **범위:** 지정한 파일·위치만 바꿨는가.
2. **정확성:** 지시한 동작이 그대로 구현됐는가.
3. **규칙:** CLAUDE.md·AGENTS.md(보안 경계, 버전 올림, 개인정보 금지, 병합 금지 지시)를 지켰는가.
4. **검증:** 테스트·CI가 통과하는가. 핵심 줄을 하나씩 일부러 고장 냈을 때 테스트가 잡는 비율은 얼마인가.
5. **자기 점검:** 지시 밖의 위험·설계 빈틈을 스스로 찾아 보고했는가. GPT·Claude와 갈리는 가장 큰 차이로 본다.
6. **비용:** Claude가 설계·프롬프트·검토에 쓴 노력(낮음·중간·높음) 대비 아낀 양.

판정은 세 가지다. 합격은 수정 없이 병합할 수 있는 경우다. 조건부 합격은 작은 보완 뒤 병합하는 경우다. 불합격은 다시 하거나 다른 곳에 맡겨야 하는 경우다.

## 시험 계획

결정 전에 세운 계획이다. 7은 원인 분석이 맡기지 않는 영역이라 시험으로 하지 않았는데, 8-1이 실제 작업에서 그 경우가 되어 불합격했다.

| 순서 | 유형 | 확인할 것 | 후보 |
|---|---|---|---|
| 3 (완료) | 문서(쉬움) | 문구 정확성, 기존 문체, 범위 | 수집기 알림 지우기가 병합된 뒤 README "휴대폰·PC 매매 기준 알림"과 `docs/moving-average-alerts.md`에 동작·제외 대상(묶음 재알림, Safari·Firefox)·병합 전 알림은 지워지지 않음을 추가 |
| 4 (완료) | 자기 점검 | 프롬프트에 일부러 빠뜨린 안전장치를 찾아 보고하는가 | 정해진 작은 구현에 "지시 밖에서 발견한 위험·빈틈을 PR의 남은 위험에 적는다"를 넣는다. 일부러 뺀 항목은 이 문서에 적지 않고 시험할 때 대화로만 남긴다(제미나이가 저장소를 읽을 수 있음) |

| 6 (5번에서 확인) | 화면 변경 | AGENTS.md의 캡처 규칙(다크, 393×852, Pretendard, 대기 회차 기준)과 버전 올림 준수 | 공개 앱의 표시·배치 변경 |

## 결정 과정

- 결정 방법은 "4(자기 점검)와 5(덜 정해진 지시)가 합격이면 공개 앱의 여러 파일 구현까지 넓히고, 4가 불합격이면 범위를 유지한다"였다. 원인 분석·설계 판단, 토큰·Secrets·권한·워크플로, 수집 저장소 병합 결정은 결과와 상관없이 맡기지 않기로 했다.
- 4는 기준이 주어진 점검으로 합격했다. 5는 구현 설계는 맞았지만 테스트 빈틈으로 조건부 합격했고, 5-1에서 보완했다. 그래서 범위를 넓혔다. 다만 4의 합격은 기준이 주어진 점검에 한하므로, 위험을 스스로 추론해야 하는 일은 넣지 않았다.
- 결정 뒤에도 시험을 더 하면 같은 평가 기준으로 시험 기록에 추가하고, 결과가 달라지면 CLAUDE.md를 고친다.

## 프롬프트 작성 요령

- 테스트 기대값은 관찰할 결과로 적는다. 예: "각 실행마다 나간 알림 수를 확인한다."
- 규칙·상태를 지우거나 숨기는 수정은 지웠다가 되돌아오는 왕복(제외 → 재편입, 끄기 → 켜기)을 실행마다 나간 알림 수와 알림내역 항목 수로 확인하게 한다.
- "지시 밖에서 발견한 위험·빈틈은 고치지 말고 PR의 남은 위험에 적는다"를 넣는다.
- 기존 코드의 안전장치(시간·횟수 제한, 재시도 기간)와 같은 수준을 맞추라고 적는다.
- 핵심 판단 조건을 잠시 일부러 고장 내 새 테스트가 실패하는지 확인하고 되돌린 뒤 결과를 보고하게 한다.
- 병합 금지와 `main` 직접 push 금지를 적는다. 관련 규칙은 요약하지 않고 원문 그대로 옮긴다.
- 실행 환경 동작(콜백 시점, 화면 이동 경로, 재시도 횟수)에 달린 구현은 그 위험을 기준으로 적어 준다. 예: "문서가 다 읽힌 뒤 조회한다."
- 실기기 증상을 받은 보완은 검토자가 원인과 고칠 방향을 정한 뒤 맡긴다. 캡처와 증상만 넘기지 않는다.
- PR 본문에 직접 확인한 것과 지시·배경으로 받은 사실을 구분해 적게 한다.
- 조사를 맡길 때는 출처 링크와 날짜를 요구하고, 검토자가 핵심 출처를 직접 연다.
- 의존성을 늘리면 안 되는 작업에는 "테스트 전용 라이브러리도 추가하지 않는다. 필요하면 먼저 묻는다"를 적는다. 적지 않으면 테스트를 강하게 만들려고 스스로 추가할 수 있다(11번 보완).

## 권한 운영

- 비공개 수집 저장소는 시험할 때만 그 저장소 하나를 임시로 허용하고, 검토가 끝나면 회수한다. 영구 허용하지 않는다. 쓰기 권한이 있으면 `main` 병합으로 Secrets를 쓰는 수집 작업까지 닿을 수 있고, 저장소 맨 위의 개인 기록 사본도 읽힌다.
- 시험 PR은 병합하지 않게 하고, 병합은 검토 뒤 사용자가 결정한다.

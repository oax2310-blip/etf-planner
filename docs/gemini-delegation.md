# 제미나이·GPT 위임 평가

제미나이에 어디까지 맡길지 정한 근거 기록이다. GPT에 맡긴 작업도 같은 표에 모델을 적어 기록한다. 결정 내용은 [CLAUDE.md의 GPT·제미나이 작업 위임](../CLAUDE.md)에 반영했고, 두 문서가 다르면 CLAUDE.md를 따른다. 아래 시험 중 그 규칙의 금지 범위(푸시)에 든 것은 사용자가 시험용으로 따로 허용한 예외다.

2026-11-12에 제미나이 모델이 바뀌어 평가를 새로 시작했다. 이전 모델의 실패·보완 기록과 거기서 나온 약점 판단은 지웠고, 이전 모델의 합격 기록만 참고로 남겼다(모델 칸에 "이전 모델"). 새 모델 기록은 13번부터다.

## 현재 기준 (제미나이 새 모델 재평가 중)

- **상태:** 새 모델의 강점·약점은 아직 정하지 않았다. 이전 모델의 합격 기록에서 확인한 것은 지시한 범위·규칙 준수, 결과만 정해 줘도 기존 코드를 읽고 맞는 함수를 골라 구현하기, 주어진 기준과 어긋난 곳 찾기다.
- **맡긴다:** 문서·문구·주석 정리(기준이 되는 사실을 주고 어긋난 곳은 보고하게 한다), 정해진 파일의 기계적 수정, 공개 앱 화면·기능의 여러 파일 구현.
- **맡겨 보고 기록한다(재시험):** 증상만 주는 버그 수정·원인 찾기, 기준 없이 위험·설계 빈틈 찾기, 다른 모델이 만든 PR 점검, 조사. 아래 제외 영역 밖에서만 맡긴다.
- **아직 맡기지 않는다:** CLAUDE.md가 제외한 파일·영역(수집기 고정 실행 파일, 토큰·저장소 분리, 외부 JSON 검증·동기화, 푸시, 저장 키·백업 호환, 매매·알림·자산 계산, 워크플로·수집 저장소·`records`). 새 모델 기록이 쌓이면 사용자가 범위를 다시 정한다.
- **조건:** 기본은 사용자가 직접 맡긴다(아래 "직접 맡길 때 붙일 프롬프트"). Claude가 프롬프트를 쓰는 경우(보안 경계·설계 판단)에는 사용자 입장의 결과, 바꿀 수 있는 파일, 핵심 경우의 테스트를 넣고, "핵심 판단을 일부러 고장 내 테스트가 실패하는지 확인하고 보고한다"를 요구한다. 병합 전에는 Claude나 GPT가 범위·규칙을 확인하고 직접 고장 내 본다. 제미나이가 낸 원인 분석·점검 지적은 검토자가 근거를 직접 확인한 뒤 반영한다. 화면 변경은 AGENTS.md의 캡처 규칙대로 확인한다.

## 평가 기준

시험마다 아래 항목을 같은 방식으로 기록한다.

1. **범위:** 지정한 파일·위치만 바꿨는가.
2. **정확성:** 지시한 동작이 그대로 구현됐는가.
3. **규칙:** CLAUDE.md·AGENTS.md(보안 경계, 버전 올림, 개인정보 금지, 병합 금지 지시)를 지켰는가.
4. **검증:** 테스트·CI가 통과하는가. 핵심 줄을 하나씩 일부러 고장 냈을 때 테스트가 잡는 비율은 얼마인가.
5. **자기 점검:** 지시 밖의 위험·설계 빈틈을 스스로 찾아 보고했는가.
6. **비용:** Claude가 설계·프롬프트·검토에 쓴 노력(낮음·중간·높음) 대비 아낀 양.
7. **점검·원인 분석을 맡긴 경우:** 지적·원인마다 근거(파일·줄, 재현 방법)가 맞는가. 틀린 지적과 놓친 문제는 몇 개인가. 확인한 것과 추측을 구분했는가.

판정은 세 가지다. 합격은 수정 없이 병합할 수 있는 경우다. 조건부 합격은 작은 보완 뒤 병합하는 경우다. 불합격은 다시 하거나 다른 곳에 맡겨야 하는 경우다.

## 프롬프트 작성 요령

Claude가 프롬프트를 쓰는 경우(보안 경계·설계 판단으로 방향을 먼저 정할 때, 사용자가 요청할 때)에 적용한다.

- "지시 밖에서 발견한 위험·빈틈은 고치지 말고 PR의 남은 위험에 적는다"를 넣는다.
- 기존 코드의 안전장치(시간·횟수 제한, 재시도 기간)와 같은 수준을 맞추라고 적는다.
- 핵심 판단 조건을 잠시 일부러 고장 내 새 테스트가 실패하는지 확인하고 되돌린 뒤 결과를 보고하게 한다.
- 병합 금지와 `main` 직접 push 금지를 적는다. 관련 규칙은 요약하지 않고 원문 그대로 옮긴다.
- 실행 환경 동작(콜백 시점, 화면 이동 경로, 재시도 횟수)에 달린 구현은 그 위험을 기준으로 적어 준다. 예: "문서가 다 읽힌 뒤 조회한다."
- 실기기 증상을 받은 보완은 검토자가 원인과 고칠 방향을 정한 뒤 맡긴다. 캡처와 증상만 넘기지 않는다. 제미나이 재시험으로 증상만 주는 경우는 예외이며, 그때는 원인 주장의 근거를 검토자가 확인한다.
- PR 본문에 직접 확인한 것과 지시·배경으로 받은 사실을 구분해 적게 한다.
- 조사를 맡길 때는 출처 링크와 날짜를 요구하고, 검토자가 핵심 출처를 직접 연다.
- 의존성을 늘리면 안 되는 작업에는 "테스트 전용 라이브러리도 추가하지 않는다. 필요하면 먼저 묻는다"를 적는다. 적지 않으면 테스트를 강하게 만들려고 스스로 추가할 수 있다(11번 보완).
- 화면 요소를 어디에 붙일지·무엇을 막을지는 포커스 같은 간접 신호가 아니라 사용자가 누른 요소를 기준으로 정하게 적는다. 가짜 DOM 테스트만으로 끝내지 않고 실제 브라우저에서 포커스가 다른 곳에 있을 때도 확인하게 한다(12번).
- 보완으로 동작의 뜻이 바뀌면 기존 테스트도 다시 일부러 고장 내 이름대로 확인하는지 보게 하고, PR 설명의 "항상 ~한다"는 확인한 경로를 적게 한다(12번).
- 점검을 맡길 때는 지적마다 파일·줄, 재현 방법, 직접 확인한 것과 추측의 구분을 적게 하고, 보고 원문을 PR 댓글로 남기게 한다(13번).

## 권한 운영

- 비공개 수집 저장소는 시험할 때만 그 저장소 하나를 임시로 허용하고, 검토가 끝나면 회수한다. 영구 허용하지 않는다. 쓰기 권한이 있으면 `main` 병합으로 Secrets를 쓰는 수집 작업까지 닿을 수 있고, 저장소 맨 위의 개인 기록 사본도 읽힌다.
- 시험 PR은 병합하지 않게 하고, 병합은 검토 뒤 사용자가 결정한다.

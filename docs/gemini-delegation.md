# 제미나이·GPT 위임 프롬프트

GPT·제미나이에 일을 맡길 때 붙이는 프롬프트와 작성 요령이다. 맡기는 범위와 점검 규칙은 [CLAUDE.md의 GPT·제미나이 작업 위임](../CLAUDE.md)을 따르고, 두 문서가 다르면 CLAUDE.md를 따른다. 옛 시험 기록과 판단 근거는 이 파일의 git 기록에 있다.

## 직접 맡길 때 붙일 프롬프트

사용자가 GPT·제미나이에 직접 맡길 때 아래를 그대로 붙이고 작업 줄만 채운다. 저장소의 CLAUDE.md·AGENTS.md가 규칙 대부분을 담고 있으므로 여기에는 검증과 보고 형식만 둔다. 바꿀 파일의 범위는 적지 않는다. 바꾼 파일이 작업에 맞는지와 제미나이 제외 대상(CLAUDE.md "GPT·제미나이 작업 위임")을 건드리지 않았는지는 병합 전 점검에서 Claude가 확인한다.

```
저장소: oax2310-blip/etf-planner. 최신 main에서 브랜치 하나로 작업한다.
작업: [사용자 입장의 결과. 무엇이 어떻게 보이고 동작해야 하는지]
규칙
- 저장소 AGENTS.md·CLAUDE.md를 그대로 지킨다.
- 저장 키·저장값·옛 기록 호환을 바꾸지 않는다. 표시만 바꾸면 그렇게 적는다.
- 라이브러리는 테스트 전용도 추가하지 않는다. 필요하면 먼저 묻는다.
- 관련 테스트를 추가하고, 핵심 판단을 하나씩 일부러 고장 내 새 테스트가 실패하는지 확인한 뒤 되돌린다.
- CSS·JS를 바꾸면 node scripts/bump-asset-version.cjs를 실행하고 --check로 확인한다.
- node --test --test-reporter=dot tests/*.cjs 통과 뒤 PR만 만든다. 병합과 main 직접 push는 하지 않는다.
- 작업하며 읽은 코드(바꾼 곳의 호출부·관련 경로 포함)에서 지시 밖 버그·위험·빈틈을 찾되 고치지 말고, PR에 파일·줄·근거와 확인/추측 구분으로 적는다. 없으면 살펴본 범위와 함께 "없음"으로 적는다.
PR 설명에 적을 것
- 바꾼 파일과 이유, 테스트 통과 수
- 고장 내기 표(고장 낸 것 → 잡은 테스트)
- 직접 확인한 것과 지시로 받은 사실의 구분
- 화면 변경이면 확인 조건(393×852·터치·다크)과 결과를 글로. 캡처·임시 파일은 커밋하지 않는다.
- 버그면 원인마다 파일·줄, 재현 방법, 확인한 것과 가설의 구분
```

점검 비용은 "PR 설명에 적을 것"이 정한다. 설명이 없으면 Claude가 처음부터 파악해야 해서 직접 구현과 비슷해진다. 점검 깊이는 CLAUDE.md대로 문서·문구는 가볍게, 화면 동작·계산·동기화는 테스트 실행·브라우저 재현·고장 내기까지 한다.

## 프롬프트 작성 요령

Claude가 프롬프트를 쓰는 경우(보안 경계·설계 판단으로 방향을 먼저 정할 때, 사용자가 요청할 때)에 적용한다.

- 테스트 기대값은 관찰할 결과로 적는다. 예: "각 실행마다 나간 알림 수를 확인한다."
- "작업하며 읽은 코드(바꾼 곳의 호출부·관련 경로 포함)에서 지시 밖 위험·빈틈을 찾되 고치지 말고 PR의 남은 위험에 적는다. 없으면 살펴본 범위와 함께 '없음'으로 적는다"를 넣는다.
- 기존 코드의 안전장치(시간·횟수 제한, 재시도 기간)와 같은 수준을 맞추라고 적는다.
- 핵심 판단 조건을 잠시 일부러 고장 내 새 테스트가 실패하는지 확인하고 되돌린 뒤 결과를 보고하게 한다.
- 병합 금지와 `main` 직접 push 금지를 적는다. 관련 규칙은 요약하지 않고 원문 그대로 옮긴다.
- 실행 환경 동작(콜백 시점, 화면 이동 경로, 재시도 횟수)에 달린 구현은 그 위험을 기준으로 적어 준다. 예: "문서가 다 읽힌 뒤 조회한다."
- 대기·종료 조건을 바꾸는 수정은 바뀐 조건이 기존 종료 경로(정상 응답, 오류, 시간초과, 취소 등)마다 어떻게 달라지는지 표로 적고 경로마다 테스트를 두게 한다. 다른 종료 경로에 생긴 회귀와 PR 설명·실제 동작의 어긋남을 여러 번 놓쳤다.
- 실기기 증상을 받은 보완은 검토자가 원인과 고칠 방향을 정한 뒤 맡긴다. 캡처와 증상만 넘기지 않는다. 증상만 주고 원인 분석부터 맡기는 경우에는 원인 주장의 근거를 검토자가 확인한다.
- PR 본문에 직접 확인한 것과 지시·배경으로 받은 사실을 구분해 적게 한다.
- 조사를 맡길 때는 출처 링크와 날짜를 요구하고, 검토자가 핵심 출처를 직접 연다.
- 의존성을 늘리면 안 되는 작업에는 "테스트 전용 라이브러리도 추가하지 않는다. 필요하면 먼저 묻는다"를 적는다. 적지 않으면 테스트를 강하게 만들려고 스스로 추가할 수 있다.
- 화면 요소를 어디에 붙일지·무엇을 막을지는 포커스 같은 간접 신호가 아니라 사용자가 누른 요소를 기준으로 정하게 적는다. 가짜 DOM 테스트만으로 끝내지 않고 실제 브라우저에서 포커스가 다른 곳에 있을 때도 확인하게 한다.
- 보완으로 동작의 뜻이 바뀌면 기존 테스트도 다시 일부러 고장 내 이름대로 확인하는지 보게 하고, PR 설명의 "항상 ~한다"는 확인한 경로를 적게 한다.
- 점검을 맡길 때는 지적마다 파일·줄, 재현 방법, 직접 확인한 것과 추측의 구분을 적게 하고, 보고 원문을 PR 댓글로 남기게 한다.
- 비용·성능 분석을 맡길 때는 절감 주장마다 근거 실행 ID와 단계별 시간을 붙이고, 줄어드는 양을 청구 단위(작업마다 1분 올림)로 계산하게 한다. 바꾸려는 단계가 그 실행에서 실제로 도는지도 확인하게 한다.
- 크기·간격·터치 영역은 CSS 계산이 아니라 브라우저에서 잰 값으로 보고하게 하고, 잰 방법(`getComputedStyle(요소,"::before").height`, 경계 밖 지점의 `elementFromPoint`)을 적게 한다. 기존 코드·테스트 주석의 숫자도 맞다고 보지 말고 같이 재게 한다.

## 권한 운영

- 비공개 수집 저장소는 그 저장소 일을 맡길 때만 그 저장소 하나를 임시로 허용하고, 검토가 끝나면 회수한다. 영구 허용하지 않는다. 쓰기 권한이 있으면 `main` 병합으로 Secrets를 쓰는 수집 작업까지 닿을 수 있고, 저장소 맨 위의 개인 기록 사본도 읽힌다.
- 맡긴 작업의 PR 병합은 검토 뒤 사용자가 결정한다.

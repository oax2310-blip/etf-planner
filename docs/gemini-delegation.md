# 제미나이 위임 평가

제미나이에 어디까지 맡길지 정한 근거 기록이다. 결정 내용은 [CLAUDE.md의 GPT·제미나이 작업 위임](../CLAUDE.md)에 반영했고, 두 문서가 다르면 CLAUDE.md를 따른다. 아래 시험 중 그 규칙의 금지 범위(푸시·수집 저장소)에 든 것은 사용자가 시험용으로 따로 허용한 예외다.

## 결정 (시험 1~5 근거)

- **특징:** 지시한 범위·규칙을 정확히 지킨다. 결과만 정해 줘도 기존 코드를 읽고 맞는 함수를 골라 구현한다. 주어진 기준과 어긋난 곳은 잘 찾는다. 반면 기준 없이 위험·설계 빈틈을 추론하지 못하고, 테스트에서 가장 까다로운 경우를 빠뜨리는 경향이 있다.
- **맡긴다:** 문서·문구·주석 정리(기준이 되는 사실을 주고 어긋난 곳은 보고하게 한다), 정해진 파일의 기계적 수정, 공개 앱 화면·기능의 여러 파일 구현.
- **맡기지 않는다:** 원인 분석·설계 판단, 위험을 스스로 판단해야 하는 일, CLAUDE.md가 제외한 파일·영역(수집기 고정 실행 파일, 토큰·저장소 분리, 외부 JSON 검증·동기화, 푸시, 저장 키·백업 호환, 매매·알림·자산 계산, 워크플로·수집 저장소·`records`).
- **조건:** 프롬프트에는 사용자 입장의 결과, 바꿀 수 있는 파일, 핵심 경우의 테스트를 넣고, "핵심 판단을 일부러 고장 내 테스트가 실패하는지 확인하고 보고한다"를 요구한다. 병합 전에는 Claude나 GPT가 범위·규칙을 확인하고 직접 고장 내 본다. 화면 변경은 AGENTS.md의 캡처 규칙대로 확인한다.

2번에서 놓친 점(2-1에서 모두 보완):

- **테스트 빈틈:** 옛 알림 재시도 취소를 "대기열이 비었다"로만 확인했다. 그 실행에서 알림이 나가지 않았는지는 확인하지 않았다. 그래서 취소 코드를 지워도 테스트가 통과했다.
- **자기 점검 없음:** 설계 누락을 스스로 찾지 못했다. 새 발송 반복에 시간 제한이 없었는데, 바로 옆 기존 발송 함수에는 90초 제한이 있었다. 만료 기기가 로그에 "재시도"로 찍히는 문제도 그대로 두었다.

3번 참고: 미국 시세 수집 예약 시각과 주말 비트코인 수집 시간이 README와 `docs/moving-average-alerts.md`에서 서로 다르다. 제미나이가 두 문서의 해당 절을 읽고도 보고하지 않았다. 일부러 심은 함정이 아니어서 판정에는 넣지 않고, 4번(자기 점검)을 판단할 때 참고 신호로 둔다.

4번 참고: 3번과 같은 "발견 사항" 지시였는데 이번에는 잘 찾았다. 이번에는 기준 사실("GitHub 자체 예약은 지웠다")이 주어져 그와 어긋나는 문장을 찾는 일이었다. 3번(기준 없이 두 문서를 맞대 보기)과 2번(기존 코드의 안전장치를 보고 빠진 것을 추론하기)은 못했다. 그래서 "주어진 기준에 비추어 점검하기는 됨, 기준 없이 위험을 추론하기는 아직 안 됨"으로 본다. 보고된 문서 오류는 모두 고쳤다.

5번 참고: 결과만 주어도 기존 코드를 읽고 맞는 함수를 골라 쓰는 설계 능력은 확인됐다. 약점은 2번과 같은 유형으로, 테스트가 쉬운 경우만 확인하고 가장 까다로운 경우를 빠뜨린다. 그래서 검토할 때 핵심 판단을 일부러 고장 내 보는 확인이 반드시 필요하다. 프롬프트에 "핵심 조건을 일부러 고장 내 테스트가 실패하는지 확인하고 보고한다"를 넣으면 스스로 확인할 수 있다(5-1). 화면 변경(버튼 추가)과 버전 규칙도 이 시험에서 확인해 시험 계획의 6번(화면 변경)을 대신한다.

6~8번 참고:

- **다른 저장소에서도 같은 특징:** Android Java 앱에서도 지시 준수와 기준 안의 자기 점검(분기 판단 표)은 웹 JS 때와 같았다. 반면 단위 테스트로 잡히지 않는 실행 환경 동작(WebView 콜백 시점, 로그인 이동 경로)의 위험은 스스로 추론하지 못했다. "기준 없이 위험 추론 못함"과 같은 유형이다.
- **조사 보고서는 출처를 확인해야 한다:** 7번은 형식은 지켰지만 "직접 확인" 표시를 그대로 믿을 수 없었다. 핵심 출처는 검토자가 직접 열어 보고, 실기기·실제 화면으로 바로 확인할 수 있는 질문은 그 확인으로 정한다.
- **확인한 것과 전달받은 것을 섞는다:** 8번의 발견 사항은 프롬프트 배경으로 준 사실을 자기가 확인한 것처럼 적었다.
- **운영 사실:** 제미나이와 검토자 환경 모두 Android SDK가 없어, 그 저장소의 AGENTS.md 규칙대로 임시 Actions로 테스트를 돌린다. 6번에서 처음에 push·PR이 빠진 것은 설정 문제여서 평가에 넣지 않았다.

## 평가 기준

시험마다 아래 항목을 같은 방식으로 기록한다.

1. **범위:** 지정한 파일·위치만 바꿨는가.
2. **정확성:** 지시한 동작이 그대로 구현됐는가.
3. **규칙:** CLAUDE.md·AGENTS.md(보안 경계, 버전 올림, 개인정보 금지, 병합 금지 지시)를 지켰는가.
4. **검증:** 테스트·CI가 통과하는가. 핵심 줄을 하나씩 일부러 고장 냈을 때 테스트가 잡는 비율은 얼마인가.
5. **자기 점검:** 지시 밖의 위험·설계 빈틈을 스스로 찾아 보고했는가. GPT·Claude와 갈리는 가장 큰 차이로 본다.
6. **비용:** Claude가 설계·프롬프트·검토에 쓴 노력(낮음·중간·높음) 대비 아낀 양.

판정은 세 가지다. 합격은 수정 없이 병합할 수 있는 경우다. 조건부 합격은 작은 보완 뒤 병합하는 경우다. 불합격은 다시 하거나 다른 곳에 맡겨야 하는 경우다.

## 결정 과정

- 결정 방법은 "4(자기 점검)와 5(덜 정해진 지시)가 합격이면 공개 앱의 여러 파일 구현까지 넓히고, 4가 불합격이면 범위를 유지한다"였다. 원인 분석·설계 판단, 토큰·Secrets·권한·워크플로, 수집 저장소 병합 결정은 결과와 상관없이 맡기지 않기로 했다.
- 4는 기준이 주어진 점검으로 합격했다. 5는 구현 설계는 맞았지만 테스트 빈틈으로 조건부 합격했고, 5-1에서 보완했다. 그래서 범위를 넓혔다. 다만 4의 합격은 기준이 주어진 점검에 한하므로, 위험을 스스로 추론해야 하는 일은 넣지 않았다.
- 결정 뒤에도 시험을 더 하면 같은 평가 기준으로 시험 기록에 추가하고, 결과가 달라지면 CLAUDE.md를 고친다.

## 프롬프트 작성 요령

- 테스트 기대값은 관찰할 결과로 적는다. 예: "각 실행마다 나간 알림 수를 확인한다."
- "지시 밖에서 발견한 위험·빈틈은 고치지 말고 PR의 남은 위험에 적는다"를 넣는다.
- 기존 코드의 안전장치(시간·횟수 제한, 재시도 기간)와 같은 수준을 맞추라고 적는다.
- 핵심 판단 조건을 잠시 일부러 고장 내 새 테스트가 실패하는지 확인하고 되돌린 뒤 결과를 보고하게 한다.
- 병합 금지와 `main` 직접 push 금지를 적는다. 관련 규칙은 요약하지 않고 원문 그대로 옮긴다.
- 실행 환경 동작(콜백 시점, 화면 이동 경로, 재시도 횟수)에 달린 구현은 그 위험을 기준으로 적어 준다. 예: "문서가 다 읽힌 뒤 조회한다."
- PR 본문에 직접 확인한 것과 지시·배경으로 받은 사실을 구분해 적게 한다.
- 조사를 맡길 때는 출처 링크와 날짜를 요구하고, 검토자가 핵심 출처를 직접 연다.

## 권한 운영

- 비공개 수집 저장소는 시험할 때만 그 저장소 하나를 임시로 허용하고, 검토가 끝나면 회수한다. 영구 허용하지 않는다. 쓰기 권한이 있으면 `main` 병합으로 Secrets를 쓰는 수집 작업까지 닿을 수 있고, 저장소 맨 위의 개인 기록 사본도 읽힌다.
- 시험 PR은 병합하지 않게 하고, 병합은 검토 뒤 사용자가 결정한다.
